# ADR-0011: The local runtime is one compose project, and `doctor` diagnoses the environment without changing it

## Context and Problem Statement

A contributor has to run the whole system locally with a single command (INFRA-03), and applications started from the IDE
have to reach the same Axon Server as services inside compose (INFRA-04). The environment that makes this work is
fragile: a pinned container engine on macOS (colima or Docker Desktop), mise-pinned tools, a DCB context in Axon Server,
Testcontainers settings and an AI tooling installation. A contributor who sees a failure needs to learn the cause and the
fix without reading the build.

Two decisions follow: how the runtime is composed, and how the environment is checked.

## Decision Drivers

- `docker compose up -d --wait` works in a fresh clone, with no flag, no `.env` and no Gradle run.
- Images come from the version catalog, pinned by digest, and the compose files hold no image literal (INFRA-09).
- Both connection scenarios work against the same Axon Server without reconfiguration: services inside compose, and
  applications on the host.
- A diagnosis must never change the machine, and each environment check must have one implementation.
- The development Axon Server has no access control, and the PostgreSQL passwords are development defaults.

## Considered Options

- A root `compose.yaml` that includes per-concern files (chosen), versus a single `compose.yaml`.
- The Axon Server DCB context created by its own setting (chosen), versus a one-shot init container that calls
  `/v2/cluster/init?dcb=true`.
- One PostgreSQL server with a database and a login role per service (chosen), versus one database with a schema per
  service, versus a PostgreSQL container per service.
- `doctor` as a shell bootstrap plus a Gradle task (chosen), versus shell only, versus Gradle only.
- A `doctor` that prints the fix command (chosen), versus one with a `--fix` mode.
- A `doctor --ci` job in CI (chosen), versus a local-only `doctor`.

## Decision Outcome

Chosen option: "an included compose project with a self-creating DCB context, and a diagnose-only `doctor`", because it
needs no helper container, keeps one source for every version, and tells the contributor what to run without running it.

### The runtime (D-23 to D-26, D-46)

- **Structure.** `compose.yaml` sets the project name and pulls in `compose/infra.yaml` through `include:`, with
  `compose/versions.env` as its environment file; later phases add services, observability and the UI as further
  files, and optional parts use profiles.
- **Images from the catalog.** `compose/versions.env` is generated by `./gradlew generateComposeVersions` from the version
  catalog (the digest-pinned Axon Server and PostgreSQL images) and is committed. `checkComposeVersions`, part of `check`,
  fails when it is stale, and `docker compose config` is validated in CI.
- **DCB context without an init container.** `AXONIQ_AXONSERVER_STANDALONE_DCB=true` makes Axon Server create the DCB
  `default` context at boot, and a fixed `hostname: axonserver` keeps the stored node name stable when the container is
  recreated (a random hostname would orphan the stored contexts). Spike 003 found that calling `/v2/cluster/init` a second
  time corrupts the single-node Raft group, which rules the init container out. Host and compose clients connect without
  reconfiguration and reconnect after restarts.
- **One PostgreSQL server, a database per service.** An init script creates a login role and a database for the query
  service and for the automation service, so each service owns everything it writes, including its Axon token store. The
  script runs once per volume.
- **Loopback only.** Every published port binds to `127.0.0.1`, because the development Axon Server has no access control and
  the PostgreSQL passwords are development defaults.
- **Both scenarios, to the depth that exists.** The host scenario is proven functionally: the conditional-append
  integration test runs against `localhost:8124`. The in-network scenario is proven at network level: a `probe` service on
  the compose network reaches Axon Server by its service name on the HTTP and the gRPC port. Functional in-network gRPC
  clients arrive with the services of Phases 3 and 6. The `Compose smoke test` CI job runs both against the stack a
  contributor starts.

### `doctor` (D-27 to D-29, D-48)

- **Entry point.** `scripts/doctor.sh` runs the checks that must work before Gradle can start or that Gradle does not
  own: mise and its tools, a Java runtime for the wrapper, the Docker engine and its image store, the Testcontainers
  settings, the pinned GSD installation against the hashes of its manifest, the global GSD defaults, the MCP servers, the
  Platform token, colima, the Claude Code release and the tracked `.claude/` files. It then runs `./gradlew doctor`, which
  holds the JVM-side checks: the Node major, the formatter binaries, the daemon JVM criteria and Testcontainers
  connectivity through the Testcontainers library itself (`:tooling:doctor`).
- **One implementation per check (D-48).** The shell delegates the checks Gradle already owns instead of repeating them. When
  Java is missing, the shell reports that as the failure and the delegated checks as skipped.
- **Diagnose only.** Every check ends as `ok`, `warn`, `fail` or `skip` with the exact fix command, and the script exits
  non-zero on any `fail`. It installs, updates, starts and deletes nothing, and never prints a secret. A `--fix` mode was
  not adopted.
- **`--ci` mode.** A separate `Doctor` CI job runs `scripts/doctor.sh --ci` on Ubuntu with Docker. The checks that only make
  sense on a developer machine (GSD, its defaults, MCP, the Platform token, colima and the Claude Code release) are
  reported as `skip`.

### Consequences

- Good, because one command starts the runtime from a fresh clone, and one command explains why it does not.
- Good, because no version appears in a compose file, and a stale generated file fails the build instead of the runtime.
- Good, because a diagnosis is safe to run at any time and in CI.
- Bad, because the in-network scenario is proven at network level only, so a gRPC problem that affects containers and not the
  host would first show up with the first service container.
- Bad, because Axon Server's own setting creates the context: a defect there cannot be worked around by a script. Upstream
  record UP-0013 shows a related trap, the v1 endpoint `/v1/public/context` reports `dcbContext: false` for the DCB
  context, which only matters to tooling that reads that endpoint.
- Bad, because of an open concern that is not verified on this version. A forum report (AxonIQ forum topic 6639, February
  2026, Axon Server Enterprise 2025.2.4) describes `standalone-dcb=true` together with a valid Platform token on fresh
  volumes leaving the `_admin` context in a pre-vote loop, so the `default` DCB context is never created; AxonIQ's
  workaround there is `axoniq.axonserver.autocluster.dcb=true`. This compose file uses `standalone-dcb` with an optional token
  on fresh volumes and was tested on 2026.1.8 without a token only. Check this combination before relying on the token with
  empty volumes.
- Bad, because `doctor` reads `.env` for the token and cannot see a variable exported only in the shell.

### Confirmation

- `scripts/test-doctor.sh` runs in CI with the other shell tests, and the `Doctor` job runs `scripts/doctor.sh --ci`.
- The `Compose smoke test` job proves the two scenarios, and `checkComposeVersions` proves the generated file is current.
- `docker compose config --quiet` runs in the lint job.

## Pros and Cons of the Options

### A root `compose.yaml` with `include:`

- Good, because each concern (infrastructure now, services, observability and the UI later) has its own file and optional
  parts use profiles, while `docker compose up` stays one command.
- Bad, because a reader follows one more indirection than in a single file. A single `compose.yaml` was the alternative and
  grows with every phase.

### The DCB context created by Axon Server's own setting

- Good, because no helper container exists to order or to fail.
- Bad, because the setting is the only lever if Axon Server changes how it creates the context.

### An init container that calls `/v2/cluster/init?dcb=true`

- Good, because the context creation would be explicit in the compose file.
- Bad, because a second call corrupts the single-node Raft group, so the container would have to be idempotent by
  construction, and it adds a startup dependency for every service (spike 003).

### One server with a database and a role per service

- Good, because each service owns everything it writes, including its token store, with one container to run.
- Bad, because the services share a server's resources and its superuser.
- A schema per service in one database would let one service's role reach another's tables unless grants are managed, and a
  container per service multiplies containers for a local runtime.

### A shell bootstrap plus a Gradle task

- Good, because the shell runs when Java or mise is missing, which is exactly when a contributor needs a diagnosis, and Gradle
  runs the checks that already exist as tasks.
- Bad, because the split needs the D-48 rule that every check has one home. Shell only would repeat the Node, formatter and
  daemon-JVM checks, and Gradle only cannot run without Java.

### Diagnose and print the fix, or fix

- Good, because a diagnosing `doctor` is safe to run at any time and in CI and never surprises a developer's machine.
- Bad, because the contributor runs the fix. A `--fix` mode changes the machine and was deferred (D-28).

### `doctor --ci` in CI, or local only

- Good, because the diagnosis then has a continuously verified implementation, with the machine-specific checks skipped.
- Bad, because it is one more CI job under the required `ci-success`.
