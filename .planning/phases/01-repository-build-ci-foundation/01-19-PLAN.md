## Phase Goal

**As a** contributor, **I want to** clone the repository, install pinned tools, and build and check the whole multi-project build with one command, **so that** every commit and pull request is automatically formatted, analysed, licence-checked and governed.

<objective>
Close review finding WR-07 completely. The author chose both parts:
- The alternate Renovate config names.
- The mise sidecar lockfiles, plus every other mise config file CI would honour.

The governed boundary must cover every file that carries the same authority as `mise.toml`, `mise.lock` and
`renovate.json5`.

Gap reason (01-REVIEW.md WR-07):
- Renovate reads exactly one config file, the first it finds. `renovate.json` (and, as verified here, `renovate.jsonc`) comes before `renovate.json5`, so a pull request adding `renovate.json` with `automerge: true` rules passes the gate without the label.
- The tracked sidecar lockfiles under `.mise/locks/**` pin the transitive dependency trees of `npm:renovate` and `pipx:reuse`, yet they are ungoverned.
- Other mise config file names merge over `mise.toml`. The reviewer left their status to be confirmed.

Verified facts this plan builds on (looked up at planning time; cite them in the file comments):
- Renovate search order (docs.renovatebot.com configuration options; Renovate source `lib/config/app-strings.ts`):
  `renovate.json`, `renovate.jsonc`, `renovate.json5`, `.github/renovate.json`, `.github/renovate.jsonc`,
  `.github/renovate.json5`, `.gitlab/renovate.json`, `.gitlab/renovate.jsonc`, `.gitlab/renovate.json5`,
  `.renovaterc`, `.renovaterc.json`, `.renovaterc.jsonc`, `.renovaterc.json5`, `package.json` (a `renovate`
  section, deprecated but still read). The source drops the `.gitlab/` names on GitHub. The documentation does not
  state that condition, so they are governed anyway, the way plan 01-17 governs the absent Groovy build scripts.
  `.github/renovate.*` is already covered by `.github/**`.
- mise (mise.jdx.dev configuration, `mise trust` and mise.lock pages):
  - mise reads config from the filesystem root down to the current directory, never below it. In one directory it reads, in precedence order:
    - `mise.local.toml`, with `.mise.local.toml` above it;
    - `mise.toml`, with `.mise.toml` above it;
    - `mise/config.toml`, then `mise/conf.d/`;
    - `.mise/config.toml`, then `.mise/conf.d/`;
    - `.config/mise.toml`, then `.config/mise/` (`mise.toml`, `config.toml`, `conf.d/`);
    - `.tool-versions`;
    - `config.local.toml` and `mise.local.toml` variants beside each of these.
  - The early-init rc files `.miserc.local.toml`, `.miserc.toml` and `.config/miserc.toml` decide which config files are read at all (`env`, `ceiling_paths`, `ignored_config_paths`, `override_config_filenames`). `[settings]` in `mise.toml` cannot affect discovery.
  - `mise install` trusts the config it reads.
  - Tools listed only in `.tool-versions` are not locked.
  - Project config can set `[env]` entries such as `_.path`.
  - Each config file's tools are checked against that file's own lockfile.
  - Environment files (`mise.<env>.toml`) load only when `MISE_ENV`, `-E` or an rc file's `env` key selects them.
- CI runs `jdx/mise-action` from the repository root (input `working_directory` defaults to `.`). The action runs `mise install --locked` and, by default, exports mise's environment and PATH entries to later steps (inputs `env` and `export_path`). It adds `--monorepo` (subdirectory config roots) only when a config declares `monorepo.config_roots`; once this plan lands, every root config that could declare it is governed.

Conclusion: CI honours every mise config and rc name in the repository root:
- the files above `mise.toml` in precedence override its pins;
- the files below it can add tools and `[env]`/PATH entries that later steps inherit;
- the rc files can redirect discovery altogether.

All of them are governed. The following stay outside, for recorded reasons:
- environment files, because only a governed file can select an environment;
- subdirectory and out-of-checkout configs, which a root-level run never reads;
- alternate lockfiles, which only matter through their governed config file;
- `.java-version` and `.nvmrc`, because CI disables mise's java and node.

Trade-off the author accepted: governing `.mise/locks/**` takes Renovate's `npm:renovate` and `pipx:reuse` bumps that
rewrite a sidecar out of the version-only exemption, because a new sidecar directory means added files. Do NOT extend
the exemption in this run. This consciously narrows the plan 01-17 prohibition "MUST NOT add an entry that makes a
D-12 automerge flow need the label" for `.mise/locks/**` only. Record it in the SUMMARY under Next Phase Readiness
as a possible follow-up. One option there is an exemption rule that accepts a bot's sidecar directory swap when it
matches a version-only `mise.toml`/`mise.lock` change.

Purpose: AIDEV-06 lists "Renovate config" among the governance files, and this covers it under every name Renovate
reads. Tool pins are governed wherever mise reads them in CI. AIDEV-08 keeps the agent asking before it edits any of
them.
