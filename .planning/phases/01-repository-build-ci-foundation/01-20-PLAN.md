## Phase Goal

**As a** contributor, **I want to** clone the repository, install pinned tools, and build and check the whole multi-project build with one command, **so that** every commit and pull request is automatically formatted, analysed, licence-checked and governed.

<objective>

gate runs from the pull request's own merge ref, so a pull request can rewrite the gate that is meant to hold it.

Gap reason (01-REVIEW.md WR-06; 01-VERIFICATION.md human item 2):
- `.github/workflows/governance.yml` triggers on `pull_request`, and its checkout takes the default ref, which for that event is the merge of the pull request head into the base.

- In the same change that touches a governed file, a pull request can make `check-pr.sh` end with `exit 0`, narrow the governed list to an entry it does not touch, or change the job, and `governance-success` goes green without the label.
- The Phase 1 research assumed the gate would not run pull request code. The implementation checks the pull request out and runs it.

Author's decision for this run:
- Record WR-06 as an accepted residual for a one-maintainer repository.
- Do not switch to `pull_request_target`, and do not add CODEOWNERS.
- Write the residual into a new ADR `docs/adr/0003-governance-gate-trust-boundary.md` in the format of ADR-0001 and ADR-0002.
- Link it from ADR-0001, whose `governance-success` required context is the thing affected.

Purpose: AIDEV-06's maintainer-approval contract states its real boundary in writing. It guards against accidental
and agent-made governed changes, not against a pull request crafted to rewrite the gate. The ADR also records when
the decision must be revisited.
Output: ADR-0003, the cross-reference in ADR-0001, and the WR-06 disposition.

1. `## Context`:
   - `governance.yml` triggers on `pull_request`. Its checkout takes the default ref, which for that event is the merge of the pull request head into the base (`refs/pull/<number>/merge`). The workflow definition, `scripts/governance/list-pr-files.sh`, `scripts/governance/check-pr.sh` and `governance/governed-paths.txt` therefore all come from the pull request's own tree.
   - So a pull request that touches a governed file can, in the same change, do any of the following, and `governance-success` turns green without the `governance-approved` label:
     - make the gate script exit 0;
     - narrow the governed list to an entry it does not touch (a list without entries fails closed, a list with one unused entry does not);
     - edit the workflow so the aggregating job passes without running the check.
   - The Phase 1 research assumed the gate would not run pull request code. The implementation does run it.
   - What else holds such a pull request today:
     - The declared ruleset (`.github/rulesets/main.json`, applied once both required contexts are green on the phase pull request) requires a pull request into `main` and squash merging, with zero approving reviews and no code-owner review.
     - No CODEOWNERS file exists.
     - Every file of the gate is itself governed (`.github/**`, `scripts/governance/**`, `governance/**`), so a pull request that touches them in good faith needs the label anyway. The protection, however, is evaluated by the code under change.
   - Plan 01-09 accepted this residual as threat T-01-20 at ASVS level 1. Review finding WR-06 asked for it to be fixed or recorded.
2. `## Decision`: keep the `pull_request` trigger and the checkout of the pull request's merge ref, and accept the residual for this one-maintainer repository. State the boundary plainly: the gate guards against accidental governed changes and against an agent that does not tamper with the gate. It is not a security boundary against a pull request crafted to rewrite it. Reasons, as bullets:
   - The single maintainer merges every pull request. Through the ruleset, every change to `main` arrives as a squash-merged pull request whose diff the maintainer reads, including a rewrite of the gate.
   - Claude Code's ask rules cover every governed path (`.claude/settings.json`, kept in step with `governance/governed-paths.txt` by `checkClaudeAskRules`), so the project's agent cannot change the gate without the author confirming the edit (AIDEV-08).
   - T-01-20 already accepted the residual at ASVS L1. The alternatives below either run pull request-adjacent logic in a privileged context or do not close the gap.
3. `## Rejected alternatives`, as a numbered list with one reason each:
   - `pull_request_target` with a checkout of the base commit only. The workflow file would come from the base branch, but the trigger runs in the base repository's context, with access to its secrets and a token that can carry write permissions. zizmor reports the trigger in its `dangerous-triggers` audit. A single later step that checks out or executes pull request content would turn it into a privileged code-execution path. For one maintainer, that risk outweighs the gain.
   - Keeping `pull_request` and checking out the base ref for `scripts/governance/**` and `governance/governed-paths.txt` in a second, sparse checkout. The workflow file itself still comes from the pull request, which can change the step to run its own copy or drop the step. The hole moves; it does not close.
   - A CODEOWNERS file with required code-owner review on the governed paths. With one maintainer, the only code owner is also the author of the pull requests, and GitHub does not accept an author's approval of their own pull request. Every governed change would need the admin bypass, and the rule adds no second reviewer.
4. `## Consequences`:
   - `governance-success` stays one of the two required contexts (ADR-0001) and keeps catching unlabelled governed changes made in good faith, whether by the maintainer or by the agent.
   - Before merging, the maintainer reads the diff of every governed file, with particular care for `.github/workflows/governance.yml`, `scripts/governance/**` and `governance/**`, because a change there can change the verdict of the check that runs on the same pull request.
   - Every `pull_request` workflow, `ci.yml` included, runs from the pull request's tree. The same reading duty applies to changes in `.github/**`.
   - The approval label is not bound to a commit (review finding WR-02). That is a separate residual, deferred by the author.
5. `## When to revisit`. Revisit this decision when either of these holds:
   - a second person gets merge rights;
   - pull requests from external contributors, including forks, become a regular way to contribute.

   Then evaluate the three alternatives again. With two maintainers, CODEOWNERS with required code-owner review becomes meaningful. With outside contributors, a base-only `pull_request_target` gate, reviewed under zizmor, becomes worth evaluating.
