Author decisions (binding, 2026-11-25): keep `cache-provider: basic` and `cache-read-only` on pull requests; keep the

too (the failing chain went from the Plugin Portal redirect to repo.maven.apache.org for kotlin-dsl's library
dependencies), in the root build and in the included build-logic build.

Facts checked while planning (2026-11-25):

- `https://maven-central.storage-download.googleapis.com/maven2/` answers 200 for
  `org/jetbrains/kotlin/kotlin-stdlib/2.4.21/kotlin-stdlib-2.4.21.pom`, its `.module` (Gradle module metadata) and its
  `.jar.sha1`, and for `org/jetbrains/kotlinx/kotlinx-serialization-bom/1.6.0/kotlinx-serialization-bom-1.6.0.pom` (the
  two artifacts of the failed run); it answers 404 for the Plugin Portal marker
  `org.gradle.kotlin.kotlin-dsl.gradle.plugin-6.7.13.pom`, which then comes from the Plugin Portal behind it.
- Declared repositories: root settings declare no `pluginManagement` repositories (Gradle's implicit Plugin Portal
  default applies) and get `mavenCentral()` with `FAIL_ON_PROJECT_REPOS` from the `courses.settings` settings plugin;
  build-logic/settings.gradle.kts declares no `pluginManagement` repositories and `gradlePluginPortal()`,
  `mavenCentral()` for dependencies. The build has no repository content filtering and no allowlist.
- Trust (accepted by the author on 2026-11-25): `gradle/verification-metadata.xml` does not exist; dependency
  verification and locking are deferred to Phase 6 (CICD-05, recorded in STATE.md). Until then, the mirror is an
  additional, unverified download source. Integrity rests on HTTPS and on the mirror's operator (Google), the same basis
  on which the build trusts Maven Central today; the `.sha1` files Gradle checks come from the same host, so they catch
  corruption, not tampering. When CICD-05 lands, dependency verification checks every artifact by checksum whatever
  repository served it, so it covers the mirrored artifacts with no mirror-specific entry.
- Init script location: `scripts/ci/` is a governed path from plan 02-24, so the script is governed without another
  governed-paths entry.

Why `init.d` instead of `--init-script` on each command line: the doctor job runs Gradle inside
`scripts/doctor.sh --ci`, and the wrapper reruns whole commands, so a file in the runner's
`${GRADLE_USER_HOME:-$HOME/.gradle}/init.d/` reaches every Gradle invocation of a job without changing doctor.sh or any
command line. Init scripts are part of the configuration-cache fingerprint; the workflow writes the same file, with the
same name and content, in every run on main and on pull requests, so configuration-cache entries that setup-gradle
restores from main stay reusable after one cache miss on the first main run with the script. Local builds have no such
file, so their configuration cache is untouched. Residual: TestKit fixture builds inside the functional-test job use
TestKit's own Gradle user home, so they still resolve from the declared repositories (the wrapper covers a 429 there
only if Gradle's message reaches the job log); record this in the SUMMARY.
