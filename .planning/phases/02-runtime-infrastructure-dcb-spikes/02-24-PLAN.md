## Phase Goal

**As a** contributor building the course domain, **I want to** run DCB on a pinned Axon Server locally and in CI with the JVM test infrastructure in place, **so that** every high-risk unknown is resolved and recorded before domain code is written.

<objective>
Close the standing exposure behind gap G-02-1: a single HTTP 429 from Maven Central during cold-cache dependency
resolution fails a required CI job (it failed `compose-smoke` at 729dcff, run 45532702352) although nothing in the
repository is wrong.

Purpose: required jobs must fail for repository reasons only. The four jobs that main does not run yet
(integration-test, functional-test, compose-smoke, doctor) start every pull-request run with an empty Gradle cache,
because `cache-read-only` restores only caches written on main; until the phase PR merges, each of them downloads the
whole build classpath from Maven Central.

Output: `scripts/ci/retry-on-rate-limit.sh` with its shell tests, every Gradle step of the required jobs wrapped, and
the wrapper governed like the other CI launchers.

Gap-closure context (agreed with the author during UAT, not to be re-litigated): the re-run of the failed job and the
push of this work are outward actions and belong to plan 02-30, not to this plan.

Why this mechanism (the smallest one that turns the transient 429 into a delay, verified while planning):

- Gradle 9.9.2 already retries a 429 inside the request: `NetworkingIssueVerifier.isTransientClientError` treats 408 and
  429 as transient, and `NetworkOperationBackOffAndRetry` makes 3 attempts with a 1000 ms initial back-off that doubles
  (about 3 s in total). Maven Central's consumption window is far longer, so Gradle then disables the repository for
  the rest of the build ("Repository ... is disabled due to earlier error").
- A mirror listed as a fallback does not help: per the Gradle user guide (Graph resolution, Repository disabling),
  Gradle does not continue to the next repository after a repository is disabled unless that repository sets
  `allowInsecureContinueWhenDisabled` (Gradle 9.3+), which Gradle names insecure because the result then depends on
  which repository answered; that option stays unused. The author decided on 2026-11-25 to add, in addition to this
  wrapper, a CI-only Maven Central mirror placed first through a Gradle init script: that is plan 02-31, which runs
  after this plan because both edit ci.yml and it lives under the `scripts/ci/**` governed path created here. This plan
  changes no repository declaration.
- The internal system properties `org.gradle.internal.network.retry.max.attempts` and `...initial.backOff` could lengthen
  Gradle's own retry, but they are unsupported internals that were renamed before (`org.gradle.internal.repository.max.retries`
  became `max.tentatives` before 5.0), so a Gradle upgrade could silently drop the protection.
- A step-level rerun on the exact 429 message is supported shell, bounded to one retry, observable through an
  annotation, and never retries a real failure, whichever host sent the 429 (Maven Central or, after plan 02-31, the
  mirror). The author kept `cache-provider: basic` and `cache-read-only` on pull requests (2026-11-25, cache-poisoning
  rationale recorded in ci.yml). The exposure also shrinks by itself once the phase PR merges and main writes caches
  for the four new jobs.
</objective>
