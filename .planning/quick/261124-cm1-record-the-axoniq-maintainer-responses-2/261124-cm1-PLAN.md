Content of the replies:

- #5326 (UP-0001): marked as an enhancement although filed like a bug. An observer API is redundant in the
  maintainer's view, because every component registered with Axon Framework can be decorated
  (https://docs.axoniq.io/axon-framework-reference/5.4/configuration/configurer/#decorators). Suggested angle for a pull
  request: a `debug` log statement with all the information in the `EventStorageEngine`; an opt-in decorator definition
  that users can enable is acceptable as well. `@Internal` on `EventStorageEngine` does not mean experimental: the
  concept stays in Axon Framework 5 and is not going to be removed; the annotation only signals "this may change, be
  careful when using". Put on 5.5.0 expecting a pull request from the reporter; the milestone is adjusted otherwise.
- #5327 (UP-0002): "This should definitely be fixed." Priority Could because `ConflictDiagnosingEventStorageEngine` is
  typically not used in production; wanted for 5.4.3, the upcoming patch release.
- #811 (UP-0003): a dispatch-side `RetryPolicy` cannot type-check, but can check that the message of the received
  exception (a `CommandExecutionException`) contains `AppendEventsTransactionRejectedException`. Handler exceptions are
  not returned as-is to the dispatcher because the exception class may be absent on the dispatching instance
  (https://docs.axoniq.io/axon-framework-reference/5.4/messaging-concepts/exception-handling/#_exception_handling_in_distributed_scenarios).
  `AppendEventsTransactionRejectedException` is deliberately not transient: retrying with the same `AppendCondition`
  cannot succeed, because it is bound to the old consistency marker; what is retryable is dispatching the command again.
  The maintainer sees merit in Axon Framework providing a retry-oriented mapping of its own exceptions, an enumeration in
  the `details` of `HandlerExecutionException`, but that is an Axon Framework pull request, not an Axoniq Framework
  concern.
- #5328 (UP-0004): first looked like a duplicate of AxonIQ/AxonFramework#3761, but #3761 concerns
  `AnnotationBasedEntityIdResolver`, this one `AnnotationBasedTagResolver`. A fair enhancement; a pull request would be
  much welcome; put on 5.7.0 as the Axoniq team's earliest convenience to tackle it themselves.
- #812 (UP-0007): "Seems like a fair addition to the `SharedAxonServerContainer`." No pull request requested. The
  related #221 that the record cites got no new reply; its text stays as it is.
